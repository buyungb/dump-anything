# Authentication

Every `/api/*` endpoint requires a valid API key. `/health` is the only
public endpoint and is intended for orchestrator probes.

## Sending the key

Every key has an authorization type: `Bearer` (the default) or `Basic`.
Use the matching `Authorization` scheme, or send the key with `X-API-Key`,
which works for either type.

```bash
# X-API-Key style (works for Bearer and Basic keys)
curl -H "X-API-Key: da_…" http://localhost:8080/api/collections

# A key created with auth_type "bearer"
curl -H "Authorization: Bearer da_…" http://localhost:8080/api/collections

# A key created with auth_type "basic"
curl -H "Authorization: Basic da_…" http://localhost:8080/api/collections
```

The value after `Basic` is the generated API key itself; it is not an
HTTP Basic username/password pair. A Basic key is rejected if it is sent
with the Bearer scheme, and vice versa.

Missing or invalid keys return `401 unauthorized`:

```json
{ "error": "unauthorized", "message": "missing api key" }
```

## Key format

```
da_<32 hex chars>           total length 35
^^^                         identifier prefix, 6 hex chars are public
   ^^^^^^^^^^^^^^^^^^^^^^^^^ 16 random bytes from the OS RNG
```

Keys are stored in the hidden `_api_keys` MongoDB collection as
`{ label, prefix, hash, auth_type, created_at, last_used_at, revoked_at }`.
The hash is SHA-256 of the plaintext; the plaintext itself is **never**
persisted. Keys created before `auth_type` was introduced remain Bearer keys.

## The bootstrap key

The first time the server starts against an empty database it provisions
one key and logs it:

```
[WARN] =================== BOOTSTRAP API KEY ===================
[WARN] source: auto-generated
[WARN] key:    da_…
[WARN] Save this now — it will not be shown again.
[WARN] =========================================================
```

Two ways to override:

- **`BOOTSTRAP_API_KEY` env var** — when set, the server persists this exact
  value as the seed key. Useful for ops automation.
- **Existing keys** — once any non-revoked key exists in the database,
  bootstrap is skipped on subsequent startups.

## Issuing labelled keys

Open **API keys** in the dashboard topbar, choose Bearer or Basic, and create
one per consumer (`from-laptop`, `ci-runner`, `webhook-x`, …). The plaintext
is shown exactly once on creation; the dashboard stores it in `localStorage`
if you click *Use in this session*.

Or via the API:

```bash
curl -X POST http://localhost:8080/api/keys \
  -H "X-API-Key: $KEY" \
  -H 'content-type: application/json' \
  -d '{"label":"ci-runner","auth_type":"basic"}'
```

## Rotation

There is no time-based expiry. To rotate:

1. Create the new key.
2. Roll it out to your callers.
3. Revoke the old one (`DELETE /api/keys/{id}` or the trash icon in the
   dashboard).

Revocation takes effect on the next request — the lookup filters on
`revoked_at IS NULL`.
